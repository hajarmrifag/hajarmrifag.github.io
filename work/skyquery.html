02 / System design

Two workflows with different jobs.

The large-data analysis and the conversational query prototype are separate paths in the published implementation.

Historical analysis

  1. Store flight records in HDFS and define Hive tables.
  2. Use PySpark for joins, enrichment and route comparisons.
  3. Export findings for analysis and presentation.

Conversational prototype

  1. The frontend sends a question and selected tables to FastAPI.
  2. A language model generates SQL using a static schema description.
  3. The service checks the query prefix, executes against SQLite, and returns up to 100 rows.

The endpoint and some service names still refer to HiveQL, but the linked query-service revision uses SQLite. The 15-million-record dataset describes the analytics project; it is not a verified row count for the prototype’s SQLite database.

03 / Technical decisions

Make failures visible and work bounded.

Give SQL generation schema context

The prompt includes table and column descriptions, and requests SQL in the execution engine’s dialect. This supplies concrete context, but does not prove that a generated answer is correct.

Limit the correction loop

For retryable execution failures, the next generation receives the previous query and error. The route makes at most three attempts in total. Validation failures return a client error instead of being retried. Successful responses include the generated SQL, columns, execution time and correction count.

Process connection comparisons by flight date

The PySpark splicing analysis filters nonstop flights for one date, caches that working set, joins possible legs, and releases the cache after collecting the result. Candidate connections must have a layover between 90 and 480 minutes.

04 / Recorded result

A concrete analysis, with its limits.

The recorded splicing run processed 95 flight dates and collected 950 comparison rows. One retained comparison for LGA → CLT → ATL showed a combined fare of $795.70 against a direct fare of $2,057.61: a difference of $1,261.91.

These are historical fare comparisons, not realized passenger savings or confirmed bookable itineraries. The script retains up to ten rows per date before its final sort, and the log contains repeated rows. The count is not 950 unique routes, and the largest retained difference is not a proven global optimum.

This produces an inspectable analytical result: a reader can follow the joins and connection constraints, then compare the output with the recorded run.

06 / What I would improve

Turn prototype boundaries into explicit guarantees.

  • Query execution: use a read-only database connection, parsed statement validation and execution limits. The current SELECT/WITH prefix check alone is not a complete security boundary.
  • Analysis quality: deduplicate candidates, rank before truncating, and align fare search snapshots before making stronger savings claims.
  • Reproducibility: document the SQLite dataset and align endpoint names with the actual execution engine.
  • Verification: add regression cases for invalid SQL, exhausted attempts and duplicate itinerary rows.

These are next steps, not features claimed as completed during the internship.
